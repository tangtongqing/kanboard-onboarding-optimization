## 1. 当前产品定位重申

本项目绝不是一个旨在完全复刻商业版或企业级 Kanboard 的冗余软件工程。

本项目的核心命题有且仅有一个：**“新手项目创建与任务拆解体验优化”**。我们的一切工作都在围绕“一个对看板方法懵懵懂懂的新手用户，如何在极低认知负荷下，快速将一个模糊的项目想法，转化为结构合理、完全可执行且符合规范的看板任务流”这一核心痛点展开。

截止目前，项目已经完成了 `V0.8.29` 前端 Clarity 页面精修与 CSS 债务清理，完成了 Figma `F01-F47` 的全高保真覆盖，并固化了最终交付包索引（PD-015）以及经 Playwright 自动化捕获的 V0.8.29 最新浏览器截图证据（PD-016-R1）。在已经奠定坚实工程实现与设计骨架的基础上，后续任何的功能增强和设计迭代，都必须克制地紧扣“新手成功完成第一次项目创建与上手使用”这一主线，杜绝任何偏离此目标的无谓堆砌。

## 2. 极致功能判断标准

为了在产品演进中追求“极致”，我们建立了一套严苛的多维度功能评估标准，防止陷入单纯堆积功能数量的低边际效应陷阱：

| 维度 | 要判断的问题 | 极致化定义与考核准则 |
| :--- | :--- | :--- |
| **新手成功率** | 是否提升用户从模糊目标到可用看板的概率 | 必须能降低“冷启动”门槛，让新手不会因为面对空白面板而茫然退弹。 |
| **首次行动** | 是否促成用户创建后 3 分钟内完成真实操作 | 首次交互（拖拽、修改、勾选）发生得越早，用户留存和激活的可能性越大。 |
| **认知负担** | 是否降低选择、理解和填写成本 | 尽量隐藏复杂的学术概念，使用小白用户听得懂的大白话及微提示。 |
| **老用户干扰** | 是否保持空白创建路径的效率 | 新手引导必须温和，绝对不能强制老用户也必须走多步向导，原有快捷通道须 100% 保留。 |
| **作品集表达价值** | 是否能讲出清晰产品决策，而不是堆功能 | 能在作品集中形成“为什么做此项优化”、“如何衡量成功”的精妙设计逻辑链条。 |
| **实现复杂度** | 是否能在静态原型中可信呈现 | 在无需复杂服务器支持下，能否在离线/localStorage 静态页面中高度仿真。 |
| **Figma/前端同步成本**| 是否会显著增加后续补图和实现负担 | 设计图覆盖率和前端还原度的对齐成本必须在可控范围内。 |
| **验证风险** | 是否依赖尚未验证的用户假设 | 标注每项功能目前属于假设状态还是有直接二手走查证据支持，克制上线。 |

## 3. 产品策略 Canvas 简版

为了明确本阶段的极致优化重心，我们将产品策略提炼为以下简版 Canvas 结构：

- **Vision（愿景）**：  
  帮助新手在完全没有看板基础的前提下，通过温和且极具启发性的场景向导与动作引导，快速从一个模糊的项目愿景迈出任务管理的第一步，降低看板方法的入门门槛。
  
- **目标细分用户 / JTBD（目标用户与核心任务）**：  
  - *细分用户*：初次尝试使用看板的学生、独立开发者、轻量化小微项目负责人（如独立创作者）。  
  - *JTBD*：当我脑子里有一个“准备期末考试”或“开发一个独立 App”的模糊目标时，我希望能把它迅速铺开成规范的看板结构，从而消除茫然感，立刻开始干活。
  
- **Value Proposition（价值主张）**：  
  无认知障碍的白话术语微文案、自带高标准行动指南的示例任务卡片、折叠式的新手热身清单，实现“所见即所学”。
  
- **Trade-offs / 不做什么（取舍边界）**：  
  - 坚决不做：企业级复杂权限分配、跨部门大型协同同步、多数据库底层切换、API Procedures 重度对接。  
  - 核心限制：绝不动摇原版 Kanboard 核心的看板流转逻辑，不重构底层的页面基础骨架。
  
- **North Star Metric（北极星指标）**：  
  **首次可用看板激活率**（即用户新建看板后，成功停留并发生有效动作的比例）。
  
- **当前阶段 OMTM（当前唯一关键指标）**：  
  **创建后 3 分钟内完成至少 1 个真实交互的比例**（即用户发生拖拽卡片、修改示例任务、或新增第一张真实卡片的激活占比）。
  
- **必要能力（Capabilities Required）**：  
  - 场景化卡片文案预设。  
  - 前端新手交互状态事件监听器。  
  - 离线持久化存储。
  
- **关键假设（Key Assumptions）**：  
  - 新手流失主因是空白板带来的“不知从何写起”的心理挫败。  
  - 高可读性、带有完成标准的示例卡文案能无形中指导用户的任务拆解。  
  
- **低成本验证实验（Validation Experiments）**：  
  - 在 V0.8.29 静态原型上硬编码 Mock 引导数据，配合专家走查，模拟小白进行二手体验走查。

## 6. 推荐 Top 5 功能包深度拆解

对 ICE 评分位列前五的功能包，我们进行细致的体验定义与落地边界划分，确保在后续阶段中做到有的放矢：

### 6.1 [立即进入 PD-018] EX-04 示例卡质量升级

- **用户问题**：模板自带的卡片（如“写大纲”）过于空洞，无法指导用户将项目目标解构成“可执行、可验证、颗粒度适中”的合理任务，导致用户依旧将其当做普通的单行 Todo List 乱堆任务。
- **为什么现在做**：这是一次纯文案升级，不需要新增代码逻辑，但对新手的“在做中教（DP02）”示范效果是即时且巨大的。
- **MVP 范围**：重构 4 个核心模板（个人学习项目、求职准备项目、小团队迭代、Bug 跟踪）的初始化卡片内容，在标题和详情描述中增加“【完成标准】”、“【预估耗时】”和“【避坑提醒】”三段式具体规范。
- **不做范围**：不改变现有的卡片布局，不设计任何新增的富文本排版标签。
- **预期体验**：用户一进入面板，双击打开示例卡，能清晰地看到一个“完美拆解的卡片范例”，立刻学会合理的编写格式。
- **对 Figma / 前端 / 截图的影响**：需要更改 Figma 和前端对应的静态文本；在重新截图和编写自动化测试时需同步更新对应的文字断言。
- **验收标准草案**：系统加载初始化模板后，默认卡片均附带实质的场景文案，无“任务一”等占位符；且文案明确写出任务的边界范围与检验条件。
- **风险与待验证点**：硬编码的文案是否对于不同的个人用户场景具有普适性。

### 6.2 [立即进入 PD-018] EX-03 创建后的首次成功 checklist

- **用户问题**：新手完成了模板创建进入主界面后，面对复杂的工具按钮依然感到无从下手，停留在界面左顾右盼，极易流失。
- **为什么现在做**：通过为用户提供极度轻量的“破冰任务”，能极大促进“3 分钟内首次行动（OMTM）”指标的达成。
- **MVP 范围**：在看板主页右下角，提供一个可折叠的卡片浮窗。预设 3 个新手入门挑战：① 拖拽卡片调整状态；② 双击编辑卡片内容；③ 新建一个你的真实卡片。通过 JS 事件监听，用户只要完成该交互，清单中自动打上绿勾。
- **不做范围**：不做复杂的跨页面导航指引，不做需要后端持久化保存的成就体系，全部在 localstorage 范围内闭环。
- **预期体验**：折叠面板伴随轻微动效，帮助新手迅速跨过交互敬畏，第一次把卡片挪进 “正在进行” 列。
- **对 Figma / 前端 / 截图的影响**：Figma 需增加此常驻浮窗的展开、折叠及点亮关键帧；前端需要在原 app.js 交互回调处加入状态判断；截图必须体现该新组件。
- **验收标准草案**：新创建项目时浮窗折叠并提供高亮闪烁提示；用户一旦完成清单中所列的操作，对应的项需实时更新为已完成状态，3项全部达成后显示庆祝动画，并允许用户一键关闭永久隐藏。
- **风险与待验证点**：该清单如果常驻，在 390px 移动端窄屏下是否会遮挡看板中处于低层的其他卡片，需要设计好避让或折叠机制。

### 6.3 [立即进入 PD-018] EX-06 字段微文案与填写帮助

- **用户问题**：新手用户在填写列、泳道、WIP 限制或新增卡片表单时，对专业术语产生认知抗拒，导致创建流失。
- **为什么现在做**：开发难度低，但对于降低整个使用流程的认知门槛（DP01）作用极为关键。
- **MVP 范围**：在创建项目、卡片编辑、泳道配置等输入框 Label 旁边，常驻一个极小的问号（Help Icon），Hover 时在上方或下方弹出极简浮层（白话释义）。
- **不做范围**：不做跳转外部长文大百科的逻辑，浮层只限制为 1-2 句的大白话生活类比。
- **预期体验**：用户在填写 WIP 限制时犹豫不决，Hover 问号后读到“WIP 限制：指本阶段最多同时堆积的任务数，防止手头活太多而一件事都做不完”，释然并顺利填写。
- **对 Figma / 前端 / 截图的影响**：设计上需定义标准的 Tooltip 样式并在表单页补全；前端可采用 CSS 自定义 tooltip 类绑定；截图需能捕获 Tooltip 打开时的状态。
- **验收标准草案**：表单中所有涉及非日常词汇（泳道、WIP等）处均存在小问号图标；Hover 后 0.2 秒内弹出释义框，移开后自动消失，文本精炼不冗长。
- **风险与待验证点**：在移动端由于缺少 Hover 状态，需改为“轻触打开释义，轻触空白处或再次点击关闭”的触控兼容事件。

### 6.4 [已完成产品定义 PD-019A] EX-10 首次拖动/修改/删除的轻引导

- **用户问题**：新手用户在进入项目后，即使看到了质量很高的示例卡片，仍不敢轻易下手去修改或删除，担心会“把演示弄坏”。
- **为什么现在做**：能进一步给用户“随意尝试”的安全感，但优先级稍逊于右下角主动式 Checklist，因此作为下一版本的升级储备。
- **MVP 范围**：在首张预设示例卡的外缘显示一个呼吸微光动效，当鼠标 Hover 或移动端聚焦时，在上方呈现一个小气泡：“您可以随时双击修改我，也可以直接将我拖拽到下一个分类哦！”
- **不做范围**：不做大面积致盲的传统黑色遮罩式“Next > Next”步骤式引导。
- **预期体验**：消除用户对示例数据的戒备心，暗示一切都是完全自由、且随时可以重置撤销的。
- **对 Figma / 前端 / 截图的影响**：设计上需要添加首张卡片悬挂气泡的指示设计。
- **验收标准草案**：引导气泡只在看板初始化且未发生任何改动时呈现，一旦用户触发了拖拽、编辑、删除等行为之一，该气泡引导需永久自行销毁。
- **风险与待验证点**：若和 6.2 节的 Checklist 浮窗同时显示，会造成视觉重点过多，带来干扰。

### 6.5 [只进行研究验证] EX-01 目标到看板的智能/规则化拆解助手

- **用户问题**：用户即使阅读了示例卡并拥有 Checklist 的驱使，面对自己的个性化任务（如：写期末论文），依然感到任务拆解无从下手。
- **为什么现在做**：这是追求“功能极致化”下对于解决“新手任务拆解”最核心的技术方向。能在作品集叙事中体现极强的趋势洞察与极致追求。但由于在静态离线原型中调用外部 LLM 既不现实也容易因为生成幻觉让新手产生困惑，因此我们**当前只做本地规则匹配（Mock AI）的设计研究与验证**。
- **MVP 范围**：在创建弹窗提供一个“写下你的项目目标”文本框。前端逻辑对用户输入进行关键词硬编码匹配（如用户输入中包含“论文”，自动触发定制匹配规则，生成“开题、检索文献、写初稿、修改、定稿”五列，以及一系列细分的具体论文卡片）。若未匹配则降级为常规模板。
- **不做范围**：本阶段绝不真去接入 OpenAI、Claude 等外部大模型 API，不做任何复杂的云端服务端集成。
- **预期体验**：用户在创建时输入“期末论文编写”，看板便如魔法般瞬间生成专属于论文写作的高匹配度栏目与指引，让其产生极高的满足感。
- **对 Figma / 前端 / 截图的影响**：设计上需要提供该文本框、动效等待加载骨架屏以及定制看板状态的视觉样图。
- **验收标准草案**：用户在输入框中输入“写论文/我的毕业论文”并点击创建时，生成的看板并非普通模板，而是自动带有特定论文写作各环节列名称及具体的论文撰写任务。
- **风险与待验证点**：用户可能会输入无法匹配的词汇，降级为常规模板时需要有极好的引导文案过渡解释。

## 7. 明确不做清单

根据 **DP07（静态作品集边界优先，避免继续功能膨胀）**，为了防止项目的工程实现走向失焦，以下 8 个方向在下一轮演进中将被明确判定为 **“坚决不做”**：

1. **插件市场继续扩展**：  
   *原因*：原版 Kanboard 拥有强大的插件系统。但插件市场和运维工具属于典型的后台管理能力，对解决“新手项目创建与拆解体验”毫无帮助，继续添加只会产生严重的静态代码负债。
   
2. **API Procedure 继续补齐**：  
   *原因*：API 属于第三方系统集成的后台纯代码逻辑。这是一个前端静态演示原型，不需要任何对接其他软件的后台接口扩展。
   
3. **部署 / 数据库 / 运维能力继续扩展**：  
   *原因*：诸如 SQLite 与 MySQL 底层切换配置、Docker Compose 部署自动化等，属于纯粹的运维工程范畴，与产品设计体验优化的核心主题完全背离。
   
4. **权限系统与多角色重构**：  
   *原因*：重构复杂的 Admin/Manager/Member 访问控制列表（ACL）。新手在第一天通常是个人小步快跑，高复杂度的权限机制不仅开发难度大，而且极易阻碍小白的快速进入。
   
5. **在线模板市场/模板商店**：  
   *原因*：支持用户在线上传、下载、点赞和分享模板。这需要高昂的云端存储、后端接口、社区运营和审核机制，严重超出了当前的静态展示边界。
   
6. **复杂看板流转自动化规则（Trigger-Action Rules）**：  
   *原因*：诸如“当某卡片在列 A 停留超过 3 天，自动指派给组长并修改状态为紧急”。这对新手来说属于极度超纲的敏捷高阶技巧，此时引入不仅增加界面复杂度，也与“新手教育桥梁”的定位不符。
   
7. **真实登录注册与短信/邮箱鉴权**：  
   *原因*：我们目前采用完全免注册、免登录的 localStorage 离线秒级进入方式。一旦强加一个登录墙，会立刻导致大量新用户放弃体验，破坏 OMTM。
   
8. **跨平台团队实时云协作（实时多人编辑）**：  
   *原因*：实现类似 Figma 的多人实时在线光标及并发冲突管理。这需要巨大的前端工程量（CRDT、Websocket），且其评估核心是“协同性能”，并非“新手创建体验”，性价比较低。

## 10. 作品集表达建议

如果在对外展示作品集时采用此路线，可以让设计故事的格局和可信度大幅度升级：

- **问题如何升级**：  
  在作品集中，我们不讲“我们如何抄出了一个 Kanboard 的仿制品”，而是讲 **“我们如何通过低成本的原型重构，破解新用户在使用轻量看板工具时的‘冷启动放弃魔咒’”**。将工程复现转化为对用户激活（User Activation）的研究。
  
- **原方案解决了什么**：  
  第一阶段的场景化向导和 Clarity 精修，在视觉上拉近了与新手的距离，清理了遗留的前端历史包袱，成功地将杂乱的项目创建流统一到了结构化模板中。
  
- **新功能包如何体现极致思维**：  
  极致不仅是视觉精美，更是对新手在看板第一天最关键的 “前 3 分钟” 行为的掌控。通过右下角的热身清单、无专业词汇阅读压力的小问号、以及能当做项目管理教材的双击示例卡文案，我们直接在无代码后端环境下，用最低的设计成本撬动了核心激活指标（OMTM）。
  
- **为什么没有继续堆系统功能**：  
  大方地解释：“在资源有限的单人项目周期内，继续复刻插件、运维接口除了堆积代码行数，没有任何独到的设计思考。我们选择将精力放在‘新手成功创建看板’这一核心流程 of 极致闭环上。” 这能体现出非常成熟、理性的**产品 owner 意识和商业设计思维**。
  
- **如何诚实说明验证限制**：  
  不要夸大成完成了物理机测试和招募式真人测试。可以在作品集总结中诚实写明：“虽然目前验证基于桌面研究、GitHub Issues 二手数据以及同行的专家级走查，但这套精巧的静态原型，已为我们下一步以极低开发成本启动‘真人在真机上的可用性测试’铺平了道路。” 这种诚实会极大增加整篇作品集的**研究可信度**。
