# Codex PRD 重构提示词模板

## 使用说明

1. 将本文件复制到需要重构 PRD 的项目目录，或把“可直接使用的提示词”全文粘贴给 Codex。
2. 先填写“项目参数”。不确定的项目参数可以留空，由 Codex 从项目文件中识别。
3. 如果允许 Codex 合并或删除旧文档，必须明确填写“文档整理权限”。
4. 建议把项目根目录作为 Codex 工作区打开，以便它同时检查 MRD、研究材料、原型、代码、测试与历史文档。
5. 默认交付 Markdown 和 Word 两种格式。Word 内应嵌入图片，不依赖本地相对路径。

## 可直接使用的提示词

你是一名资深产品经理、UX 设计评审者和产品文档架构师。请在当前项目工作区内，对现有 PRD 及其关联文档进行证据驱动的重构，并完成可供产品、设计、研发和测试共同使用的正式交付件。

这不是只改目录或润色文字的任务。你需要完成项目资料盘点、证据核对、文档去重与合并建议、PRD 信息架构重建、角色重新划分、需求补全、图表与原型编排、Word 转换和逐页质量检查。不要只给建议或大纲，直接完成文件修改与交付。

### 一、基本原则

1. PRD 是当前产品需求的唯一事实源，回答“本期需要实现什么、为什么实现、如何验收”。
2. MRD 负责市场、用户问题、机会与竞争依据；PRD 引用 MRD 结论，不大段复制市场分析。
3. 已实现能力、目标需求、未来目标和待验证假设必须明确区分，不得混写。
4. 不能把静态原型、演示结果或自动化检查结果写成真实用户效果。
5. 缺少用户研究、埋点或可用性数据时，要明确写为证据限制或待验证假设，不得编造数据。
6. 当前版本之外的其他能力统一归入“未来目标”，不得悄悄进入本期范围和验收标准。
7. 内容要完整但避免重复。同一结论只保留一个权威位置，其他位置使用链接或简短引用。
8. 对能够从项目文件、代码、原型或测试记录中确认的内容直接核对；只有会显著改变产品范围、角色或验收口径的问题才向我提问。
9. 如需做合理假设，明确标记“假设”“证据不足”或“待确认”，说明依据及可能影响。
10. 不得删除原始研究证据、设计源文件、测试记录、原型图片或版本记录。

### 二、先盘点项目，再开始写 PRD

先递归检查项目目录，至少覆盖：

- 项目治理与 README；
- MRD、市场研究、用户研究、访谈脚本和研究结论；
- 旧版 PRD、功能规格、用户故事、验收标准；
- 流程图、信息架构、状态机、设计原则；
- 低保真与高保真原型、设计图和 Figma 归档；
- 实现代码、演示入口、数据结构与本地状态；
- 测试报告、回归记录、自动化检查和验证证据；
- 路线图、版本记录、风险与待决策记录。

形成内部“需求证据矩阵”，至少记录：

| 需求/结论 | 来源文件 | 证据类型 | 当前状态 | PRD 落点 | 是否待确认 |
|---|---|---|---|---|---|

对文档做以下分类：

- 保留：具有唯一证据价值或持续维护价值；
- 合并：内容高度重复，应并入权威文档；
- 引用：不复制正文，只从 PRD 链接；
- 归档：历史过程有价值，但不应出现在当前工作流；
- 删除候选：内容已完整合并且不存在独立证据价值。

根据“文档整理权限”行动：

- “仅建议”：只输出清单，不修改或删除旧文档；
- “允许合并但不删除”：完成内容合并，保留原文件；
- “允许合并并删除已确认冗余”：先核对精确路径和合并落点，再删除已经完整吸收、可由 Git 恢复的冗余文档。

不得因为文件名相似就直接删除。删除前必须确认目标内容已经进入新的权威文档，并保留相关链接或版本信息。

### 三、PRD 必须采用的主体结构

PRD 使用以下 8 章结构。可以增加必要的三级标题，但不要改变一级章节含义。

#### 一、产品简介

至少包括：

1. 文档目的；
2. 产品背景与问题；
3. 本期范围；
4. 未来目标；
5. 本期不做；
6. 名词术语；
7. 证据边界与已知限制。

要求：

- “本期范围、未来目标、本期不做”必须彼此互斥；
- 未来能力写明进入条件，不进入本期验收；
- 若存在 MRD，在封面或本章建立明确对应关系；
- 写清楚哪些结论来自研究、原型、代码或静态检查。

#### 二、用户角色描述

不要直接把市场人群、职业、部门或泛化 Persona 当成产品角色。角色应按照会直接改变产品行为的因素划分，例如：

- 用户选择的关键路径；
- 用户所处的生命周期或激活状态；
- 用户当前目标和熟练度；
- 用户是否已完成、关闭或跳过引导；
- 用户是否拥有会改变页面或操作的权限。

先回答：

1. 哪些差异会导致页面、流程、默认值、提示或验收规则不同？
2. 哪些只是市场标签，不应成为产品角色？
3. 一个用户是否会在不同状态之间迁移？

至少输出：

- 角色划分原则；
- 角色表：角色 ID、名称、进入条件、核心目标、产品策略、退出条件；
- 市场人群与产品角色的映射关系；
- 角色状态迁移图；
- 角色体验矩阵。

角色数量以“最少但足够解释产品行为”为原则，避免为每类人群创建一个角色。

#### 三、产品概述

至少包括：

1. 产品目标；
2. 成功指标；
3. 产品功能结构；
4. 总体流程；
5. 功能摘要；
6. 功能优先级矩阵。

成功指标必须区分：

- 未来真实产品实验目标；
- 当前已经取得的结果；
- 尚未验证的研究假设。

如没有真实数据，写目标方向、计算口径、研究门槛和所需样本，不得写成已达成结果。

功能优先级至少使用 P0/P1/P2 或等价方式，并给出判断依据。可以同时使用“用户价值 × 实施复杂度”矩阵。

#### 四、功能需求说明

这是 PRD 的主体。高保真原型属于功能需求正文的一部分，应放在对应功能模块内，而不是全部堆放在附件。

每个功能模块统一使用以下结构：

1. 功能 ID、名称和优先级；
2. 目标；
3. 主要角色；
4. 前置条件；
5. 触发条件；
6. 业务规则；
7. 页面与结构；
8. 状态与异常；
9. 交互规则；
10. 数据对象、状态持久化与事件；
11. 验收标准；
12. 依赖；
13. 高保真原型。

业务规则使用稳定的需求 ID，例如 `FR-01`；验收标准使用 `AC-01`。每条验收标准必须可观察、可复现、可转成测试用例。

功能需求要覆盖：

- 默认状态；
- 空状态；
- 加载中；
- 成功状态；
- 校验失败；
- 服务或持久化失败；
- 关闭、取消和返回；
- 重复操作；
- 删除或不可逆操作；
- 刷新与恢复；
- 多项目或多对象隔离；
- 桌面端和移动端差异；
- 键盘、触屏和焦点行为；
- 浮层、弹窗、抽屉、Tooltip、Popover 的优先级和互斥关系。

高保真原型要求：

- 先搜索项目中的现有高保真资产并核对其状态；
- 每张原型必须有编号、标题和对应需求 ID；
- 原型应尽量完整展示核心页面、关键状态、异常状态和移动端适配；
- 原型与文字冲突时，以 PRD 的业务规则和验收标准为准，并记录设计待修项；
- 没有原型的关键状态应列入“原型缺口”，不能假装已经存在；
- 如果任务范围允许创建设计，则补充高保真设计；否则给出可直接交给设计师或 Figma 的页面级设计 Brief。

#### 五、其他产品需求

根据项目实际情况选择并补齐：

1. 性能与响应目标；
2. 监控与分析需求；
3. 兼容性矩阵；
4. 无障碍要求；
5. 数据、安全与隐私；
6. 内容与国际化；
7. 降级与恢复。

要求：

- 静态原型的检查通过数不能当成生产性能结果；
- 事件名称、触发条件、必要参数和禁止采集的信息要写清楚；
- 兼容性写目标环境、视口和验收方法；
- 本地存储不得描述成安全存储；
- 无障碍至少覆盖键盘、焦点、对比度、触控目标和非颜色状态表达。

#### 六、风险分析

至少包括：

1. 概率—影响风险矩阵；
2. 风险 ID、风险描述、概率、影响和等级；
3. 预防措施；
4. 发生后的应对；
5. 风险处置决策图；
6. 需求变更门槛。

风险必须覆盖：

- 用户证据不足；
- 范围膨胀；
- 原型与需求不一致；
- 引导过多或零打扰失败；
- 状态冲突；
- 本地数据损坏或隔离失败；
- 移动端与兼容性风险；
- 把静态演示误写为生产能力。

#### 七、相关文档

使用表格列出：

| 类型 | 文档 | 用途 |
|---|---|---|

至少关联：

- MRD；
- 用户研究；
- 流程与信息架构；
- 交互与状态规格；
- 高保真原型清单；
- 视觉规范；
- 测试与验证；
- 路线图；
- 版本记录。

链接使用相对路径，并验证目标文件确实存在。不要链接已经删除或改名后不存在的文件。

#### 八、附件

至少包括：

1. 原型与演示入口；
2. 高保真资产索引；
3. 当前实现结果与验证记录；
4. 待确认问题与决策记录；
5. 修订记录。

“当前实现结果”只描述当前可证明的事实，并明确其不能替代第 3、4、5 章的目标要求。

### 四、必须使用的图表

PRD 不能只有文本。根据实际内容选择并插入必要图表，避免为了装饰而画图。

优先考虑：

- 产品功能结构图；
- 用户角色状态迁移图；
- 总体业务流程图；
- 关键功能流程图；
- 页面或信息架构图；
- 状态机；
- 时序图；
- 浮层优先级或互斥矩阵；
- 角色体验矩阵；
- 功能优先级矩阵；
- 原型状态覆盖矩阵；
- 概率—影响风险矩阵；
- 风险处置决策图；
- 需求—原型—验收追踪矩阵。

图表选择规则：

- 三步以上且存在分支的过程使用流程图；
- 层级、模块和依赖使用结构图；
- 状态变化使用状态机；
- 多参与者交互使用时序图；
- 多维对比使用矩阵或表格；
- 单一事实或简单两步操作不需要画图。

Mermaid 图必须语义正确、标签不重叠、字号可读、方向适合页面。过高或过宽的图要改为分组、双列、横向或拆图，不能直接缩成看不清的小图。

### 五、文档合并与去重规则

重构时优先建立以下权威关系：

- 市场与机会结论：MRD；
- 当前需求与验收：PRD；
- 页面和视觉细节：UX/设计文档；
- 验证结果：测试或验证文档；
- 未来能力：路线图；
- 历史变更：版本记录。

PRD 内只保留理解和交付需求所必需的内容。过长的研究过程、设计探索过程、测试日志和实现过程移到对应文档，PRD 使用结论和链接。

合并后检查：

1. 是否存在两个仍被视为权威的 PRD；
2. 是否存在标题不同但正文高度重复的文档；
3. 相关文档链接是否失效；
4. README、项目结构说明和版本记录是否需要更新；
5. 被删除内容是否已经进入新的权威文档；
6. 是否误删了独立证据或历史记录。

### 六、Markdown 交付要求

输出正式 Markdown PRD：

```text
docs/02-requirements/PRD-<项目名称>.md
```

要求：

- 使用真实 Markdown 标题层级；
- 图片使用经过验证的相对路径；
- 表格列数适度，避免在 Markdown 和 Word 中严重拥挤；
- Mermaid 代码块可以保留在 Markdown；
- 不使用手工空格模拟排版；
- 不使用大量重复的“说明性废话”；
- 语言清晰、具体、可测试；
- 文件顶部记录版本、日期、状态、产品负责人、协作角色和对应 MRD。

### 七、Word 交付要求

同时生成正式 Word 文件：

```text
docs/02-requirements/PRD-<项目名称>-<目标版本>.docx
```

Word 必须满足：

1. 图片实际嵌入 DOCX，不依赖外部图片路径；
2. Mermaid 图先渲染为清晰 PNG，再嵌入 Word；
3. 使用真实的 Heading 1/2/3 标题样式；
4. 使用真实项目符号和自动编号，不用手工字符伪造；
5. 每组有序列表从 1 开始；
6. 表格使用明确列宽、单元格边距和重复表头；
7. 避免表头孤立在上一页、单行修订记录被拆页；
8. 图片与图注保持在同页；
9. 中文字体使用常见可用的中文字体，英文和代码字体保持清晰；
10. 封面包含项目名、PRD 名称、版本、日期、状态和对应 MRD；
11. 包含目录页、页眉、页脚和页码；
12. 所有关键图片具有有意义的替代文本。

高保真原型按功能出现顺序嵌入，宽屏原型使用页面可读宽度，移动端原型保持合理高度。不要为了塞进一页而把原型缩到不可读。

### 八、质量检查与完成标准

交付前必须执行完整检查，不要以“文件已生成”作为完成。

#### 内容检查

- 8 个一级章节齐全；
- 本期范围、未来目标、本期不做一致；
- 用户角色会真实改变产品行为；
- 每个核心功能都有规则、状态、异常、数据/事件和验收标准；
- 验收标准能够转成测试用例；
- 高保真原型与功能需求对应；
- 当前结果、目标和假设没有混淆；
- MRD、PRD、设计、测试和路线图边界清楚；
- 相关链接可用；
- 待确认问题集中记录，不散落在正文。

#### 图表检查

- 图表不是装饰，而是在解释流程、结构、状态或矩阵；
- 所有标签完整、无重叠；
- Word 中的 Mermaid 图已转为 PNG；
- 原型、流程图和矩阵均有编号和图注；
- 图表在 100% 缩放下可读。

#### Word 结构检查

- 图片全部为嵌入式对象；
- 标题层级可以被 Word 导航窗格识别；
- 列表编号正确重启；
- 表格列宽一致，跨页表头重复；
- 图片替代文本齐全；
- 无异常空白页；
- 无裁切、溢出、重叠或乱码。

#### 逐页视觉检查

将最终 DOCX 导出为 PDF 或逐页 PNG，检查每一页，重点关注：

- 封面和目录；
- 标题孤行；
- 表头孤立；
- 表格行拆分；
- 图片和图注分离；
- 流程图文字过小；
- 原型裁切；
- 页眉页脚冲突；
- 末页修订记录断页；
- 大块无意义空白。

发现问题后修改源文件并重新导出，直到检查通过。

如环境提供文档审计工具，还要执行：

- 图片类型与嵌入审计；
- 标题层级审计；
- 表格几何审计；
- 章节与页边距审计；
- 无障碍审计。

### 九、工作过程中的沟通方式

开始时只需告诉我：

1. 找到的主要资料范围；
2. 你准备如何划分角色；
3. 你判断的本期范围与未来目标；
4. 是否发现会显著改变 PRD 的阻塞问题。

只有以下问题需要暂停并询问：

- 不同资料对本期核心目标存在根本冲突；
- 两种角色划分会导致完全不同的产品流程；
- 缺少关键产品决策，无法安全判断 P0 范围；
- 需要删除文件但未获得对应权限；
- 需要创建新的高保真设计，而现有资料不足以确定设计方向。

其他缺失信息使用最保守、可回退的假设继续，并在“待确认问题与决策记录”中说明。

### 十、最终交付清单

完成后给出简洁交付说明，至少包括：

1. 新 PRD Markdown 文件路径；
2. 新 PRD Word 文件路径；
3. 是否创建或补充 MRD；
4. 合并、归档或删除了哪些文档；
5. 角色划分结果；
6. 本期范围和未来目标的关键变化；
7. 图表数量与高保真原型数量；
8. 仍待确认的关键问题；
9. 执行过的质量检查及结果。

不要只在聊天中粘贴整篇 PRD；应把完整内容写入项目文件，并提供可点击的交付路径。

## 本模板的默认判断

- 其他能力后续补足，作为未来目标；
- 用户角色按照会改变页面、流程和引导策略的行为因素划分；
- 高保真原型放在功能需求正文中，并尽量完整展示；
- 必要的流程图、结构图、状态图和矩阵必须提供；
- PRD 既要完整，也要明确证据边界；
- Word 是正式评审与交付格式，Markdown 是可维护的需求事实源。
