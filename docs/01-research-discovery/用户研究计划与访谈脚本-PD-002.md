## 1. 研究目标

### 核心研究问题

1. 新手面对空白 Kanboard 时，是否真的会卡住？卡在哪里？
2. 模板是否能降低首次创建成本？降低多少？
3. 示例卡是否能帮助新手理解任务粒度？
4. 字段微文案是否能减少填写疑惑？
5. 老用户是否会被新手功能打扰？

### 验证假设清单（来自 PD-001 §6）

| 假设 | 验证方法 | 优先级 |
|---|---|---|
| 新手面对空白项目确实会卡住 | 可用性测试：给新手一个空白 Kanboard，观察是否能独立完成第一张看板 | P0 |
| 模板能降低首次创建成本 | 对比测试：空白创建 vs 模板创建的首次完成率和耗时 | P0 |
| 示例卡能帮助理解任务粒度 | 可用性测试：观察新手是否参考示例卡的写法 | P1 |
| 字段微文案能减少填写疑惑 | 可用性测试：观察新手对负责人、优先级、截止时间的理解 | P1 |
| 老用户不会被新手功能打扰 | 可用性测试：给老用户使用空白创建路径，观察是否有干扰 | P1 |

## 3. 研究对象与招募条件

### 目标用户分组

| 分组 | 画像 | 招募条件 | 人数 | 招募渠道 |
|---|---|---|---|---|
| A：学生/学习者 | 作品集准备中的学生或产品学习者 | 正在准备课程项目、竞赛或求职作品集；有任务管理意愿但项目管理经验弱；未使用过 Kanboard 或类似看板工具 | 2-3 人 | 同学、学习社群、课程群 |
| B：个人开发者 | 个人开发者或工具型用户 | 正在管理开源项目或个人产品；有技术能力但不一定愿意配置复杂工具；可能用过 TODO 工具但未用过看板 | 2-3 人 | 开发者社群、技术论坛、朋友圈 |
| C：轻量团队负责人 | 轻量团队负责人或小组协作者 | 负责 2-5 人小团队的任务推进；有协作需求但不想引入复杂系统；可能用过 Excel/飞书/Notion 管理任务 | 1-2 人 | 工作同事、项目组、朋友圈 |

### 招募筛选标准

**必须满足**：
- 年龄 18-35 岁
- 有任务管理意愿（至少用过 TODO 清单或类似工具）
- 能接受 30-45 分钟的远程或面对面测试
- 能用普通话沟通

**排除条件**：
- 当前正在使用 Kanboard（已有经验会影响新手行为观察）
- 产品经理或项目经理专业人士（已有看板方法论，不代表新手行为）
- 无法在测试期间保持专注

### 招募话术模板

> 你好，我正在做一个看板工具的体验优化项目，想邀请你帮忙测试一个原型页面。测试大约 30-45 分钟，不需要任何费用，只需要你按照自己的真实想法操作和反馈。你的参与对我的产品设计非常有帮助。请问你有时间吗？

## 4. 研究方法

### 方法选择

| 方法 | 样本量 | 时长 | 目的 | 可行性 |
|---|---|---|---|---|
| **小样本可用性测试** | 5-8 人 | 30-45 分钟/人 | 观察新手创建看板的完整行为路径 | 高（学习实战项目可行） |
| **半结构化访谈** | 5-8 人（与可用性测试合并） | 10-15 分钟/人 | 了解用户的任务管理习惯和对模板的态度 | 高（可与测试合并执行） |
| **桌面研究回顾** | - | - | 回顾已有竞品分析和用户假设 | 已完成 |

### 不采用的方法及理由

| 方法 | 不采用理由 |
|---|---|
| 大规模 A/B 测试 | 需要真实后端和大量用户样本，静态原型无法支撑 |
| 远程无监督测试 | 无法观察用户行为和卡住点，数据质量低 |
| 大规模问卷调查 | 无法观察行为，只能获取态度数据，不适合验证"是否卡住" |
| 日记研究 | 周期太长，不适合学习实战项目的时间约束 |

### 执行方式

由于本项目是学习实战项目，建议采用以下执行方式：

1. **找同学/朋友做测试**：通过个人社交圈招募 5-8 人，优先覆盖 A 组（学生/学习者）和 B 组（个人开发者）。
2. **远程或面对面**：如果面对面不可行，使用屏幕共享工具（如腾讯会议、飞书）进行远程测试。
3. **使用静态原型**：测试使用 `index.html` 静态原型，不涉及后端。
4. **录音/录屏**：征得同意后录屏，便于后续回看分析。
5. **控制顺序偏差**：参与者同时测试路径 A 和路径 B 时，建议一半先做空白创建、一半先做模板创建，避免第二条路径因为已经熟悉界面而显得更顺畅。
6. **明确完成判定**：测试前定义“可用看板”为至少包含 3 个合理列、3 张可执行任务卡，并且用户能说清楚下一步会如何推进任务。

## 5. 访谈提纲

### 开场（3 分钟）

> 你好，感谢你来帮忙测试。我正在优化一个看板工具的新手体验。今天的测试不是考试，没有对错之分。我会给你一个任务，你按照自己的想法操作就行，有任何感受随时告诉我。我会录屏用于后续分析，不会分享给其他人。你准备好了吗？

### 背景了解（5 分钟）

1. 你平时用什么工具管理任务或待办事项？（TODO 清单、日历、Excel、Notion、飞书等）
2. 你有没有用过看板类工具？（Trello、Kanboard、WeKan、Jira 等）
3. 你最近有没有一个想管理的项目或任务？（用于后续引导创建）

### 可用性测试（15-20 分钟）

详见 §6 可用性测试任务。

### 回顾访谈（10 分钟）

1. 你觉得刚才的操作哪里最顺畅？哪里最卡？
2. 你觉得"从模板开始"这个功能对你有帮助吗？为什么？
3. 你觉得示例卡片对你理解任务粒度有帮助吗？你会保留还是删除？
4. 如果你来管理一个项目，你会选择空白创建还是从模板开始？为什么？
5. 你觉得这个工具适合你的使用场景吗？有什么建议？

### 结束（2 分钟）

> 感谢你的时间和反馈。你的意见对我的项目非常有帮助。如果后续有问题想再确认，可以联系我吗？

## 6. 可用性测试任务

### 路径 A：从空白项目开始（10 分钟）

**任务说明**：

> 假设你是一个正在准备求职作品集的学生。你想用这个看板工具来管理你的作品集准备过程。现在这个看板是空白的，请你从头开始，创建一个能帮你管理作品集准备任务的看板。你需要决定有哪些列、有哪些任务。完成后告诉我你觉得这个看板"可以用"了。

**观察点**：
- 用户第一步做什么？（建列？建任务？看界面？）
- 用户是否知道应该有哪些列？列名是什么？
- 用户创建了多少张任务卡？任务粒度如何？
- 用户是否使用了负责人、优先级、截止时间等字段？
- 用户花了多长时间？
- 用户在哪些步骤卡住了？卡了多久？
- 用户最终是否觉得看板"可以用"了？

### 路径 B：从模板开始（10 分钟）

**任务说明**：

> 现在请你用另一个方式创建项目。这次你可以选择"从模板开始"。同样假设你要管理求职作品集准备过程。请你选择一个合适的模板，创建项目，然后看看生成的内容。如果有不符合你需求的地方，你可以修改。完成后告诉我你觉得这个看板"可以用"了。

**观察点**：
- 用户是否注意到"从模板开始"的入口？
- 用户选择了哪个模板？选择过程是否流畅？
- 用户看到模板生成的列和示例卡后，第一反应是什么？
- 用户是否修改了示例卡？怎么修改的？
- 用户是否理解示例卡的写法？
- 用户是否理解列的含义和流转方式？
- 用户花了多长时间？
- 用户最终是否觉得看板"可以用"了？

### 路径 C（可选）：老用户空白创建（5 分钟）

**任务说明**：

> 假设你已经用这个工具管理过几个项目了，现在想快速创建一个新的空白项目。请你用最顺手的方式创建一个空白项目。

**观察点**：
- 用户是否能找到空白创建入口？
- 空白创建路径是否被模板入口干扰？
- 用户创建空白项目是否顺畅？

## 7. 观察指标与记录表

### 核心观察指标

| 指标编号 | 指标名称 | 定义 | 测量方式 |
|---|---|---|---|
| M1 | 是否完成创建 | 用户是否完成了"创建一个可用看板"的任务 | 是/否 |
| M2 | 创建耗时 | 从开始操作到认为"可以用"的时间 | 秒表计时 |
| M3 | 卡住次数 | 用户在操作过程中明显停顿、犹豫或求助的次数 | 观察计数 |
| M4 | 卡住点 | 用户卡住的具体步骤 | 记录步骤名称 |
| M5 | 是否理解列结构 | 用户创建的列是否符合看板基本结构（待办/进行中/完成） | 判断 |
| M6 | 是否理解示例卡 | 用户是否参考示例卡的写法创建自己的任务 | 观察 |
| M7 | 是否修改示例卡 | 用户是否把示例卡修改为自己的任务（路径 B） | 是/否 |
| M8 | 模板是否有帮助 | 用户主观评价模板对创建过程的帮助程度 | 1-5 分（访谈） |
| M9 | 示例卡是否有帮助 | 用户主观评价示例卡对理解任务粒度的帮助程度 | 1-5 分（访谈） |
| M10 | 老用户是否被打扰 | 老用户在空白创建路径中是否感到模板入口是干扰 | 观察+访谈 |

### 可用看板判定标准

为了让路径 A 和路径 B 可比较，本研究暂定“可用看板”满足以下条件：

- 至少包含 3 个能表达进展的列，例如待办、进行中、完成，或与场景相符的等价列。
- 至少包含 3 张具体、可执行的任务卡，而不是只有模糊目标。
- 用户能解释至少 1 张任务卡为什么放在当前列。
- 用户能说出下一次打开看板时会更新什么内容。

如果用户主观认为“可以用”，但不满足以上标准，记录为“主观完成、客观未完成”，并在观察笔记中说明原因。

## 8. 结果分析方法

### 定量分析

| 分析内容 | 方法 | 目的 |
|---|---|---|
| 完成率 | 计算 M1 各路径的完成百分比 | 判断模板是否提升首次创建成功率 |
| 耗时对比 | 计算 M2 路径 A 和路径 B 的平均耗时 | 判断模板是否缩短创建时间 |
| 卡住频率 | 计算 M3 的平均卡住次数 | 识别主要卡住点 |
| 帮助度评分 | 计算 M8、M9 的平均分 | 判断模板和示例卡的主观价值 |

### 定性分析

| 分析内容 | 方法 | 目的 |
|---|---|---|
| 卡住点归类 | 将 M4 卡住点按步骤归类，统计频率 | 识别需要重点优化的步骤 |
| 行为路径还原 | 按时间线还原每个用户的操作路径 | 发现共性行为模式和差异 |
| 用户原话提取 | 提取访谈中关于模板、示例卡、列结构的关键原话 | 为 PRD 提供用户语言证据 |
| 设计原则验证 | 对照 PD-001 §9 的 5 条设计原则，检查用户行为是否支持 | 验证设计原则的有效性 |

### 结论输出格式

研究完成后，结论应包含：

1. **假设验证结果**：每个假设的验证状态（证实/证伪/部分证实）。
2. **关键发现**：3-5 条最重要的发现，附用户原话和行为证据。
3. **设计建议**：基于发现的 3-5 条设计建议，用于指导 PRD 和原型设计。
4. **未验证问题**：研究过程中发现的新问题，需要后续验证。

## 9. 研究边界与伦理注意事项

### 研究边界

| 边界 | 说明 |
|---|---|
| 样本量 | 5-8 人，不具备统计显著性，只能发现明显的问题和趋势 |
| 用户类型 | 以学生和个人开发者为主，轻量团队负责人样本可能不足 |
| 原型限制 | 使用静态原型，无真实后端、真实登录、真实数据，可能影响用户投入度 |
| 执行环境 | 可能是远程测试，无法完全控制测试环境 |
| 研究者偏差 | 研究者同时是项目设计者，可能存在确认偏差 |

### 伦理注意事项

| 事项 | 处理方式 |
|---|---|
| 知情同意 | 测试前明确告知：测试内容、录屏用途、数据保密、自愿参与 |
| 隐私保护 | 不收集真实姓名、联系方式以外的个人信息；录屏仅用于研究分析 |
| 自愿退出 | 参与者可随时退出，不需要理由 |
| 结果使用 | 研究结果仅用于本项目的产品设计，不用于商业用途 |
| 感谢回馈 | 可以考虑请参与者喝咖啡或送小礼物作为感谢 |

### 知情同意话术

> 在开始之前，我想告诉你：这个测试大约 30-45 分钟，我会录屏用于后续分析。你的反馈只会用于我的产品设计项目，不会分享给其他人。你可以随时退出，不需要理由。请问你同意参加吗？

### 如何进入 PD-003 PRD

1. **执行研究**：按本计划执行 5-8 人的可用性测试和访谈。
2. **填写记录表**：在测试过程中填写 §7 的记录表。
3. **分析结果**：按 §8 的分析方法整理定量和定性数据。
4. **输出结论**：形成关键发现和设计建议。
5. **输入 PRD**：将验证后的假设、关键发现和设计建议作为 PD-003 PRD 的输入。

### 如果无法执行真实研究

如果由于时间或资源限制无法执行真实用户研究，可以采取以下替代方案：

1. **桌面研究增强**：进一步收集 Kanboard 社区、GitHub Issues 和论坛中关于新手上手的用户反馈。
2. **专家评审**：邀请 1-2 位有看板使用经验的朋友作为"专家用户"进行 walkthrough。
3. **自我测试**：设计者自己以新手视角走查两条路径，记录卡住点和感受。
4. **标注假设置信度**：在 PRD 中明确标注哪些结论来自真实研究、哪些仍是假设。

**注意**：如果采用替代方案，必须在 PRD 中明确声明研究的局限性，不能将假设当作已验证结论。
